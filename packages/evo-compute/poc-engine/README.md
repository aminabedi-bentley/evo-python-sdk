# POC: generated stubs over a generic runtime engine

A self-contained proof of concept for *"
Static DX in the proposed generic compute engine: generated type stubs."* 

It demonstrates the central claim: **execution stays generic and live, while a
generated `.pyi` stub gives full static IDE/type-checker DX**, and the two are the
same call shape — `poc_compute_engine.geostatistics.kriging.run(...)`.

## Layout

```
poc-engine/
  poc_compute_engine/
    __init__.py            # RUNTIME: PEP 562 __getattr__/__dir__ (dynamic topics)
    _engine.py             # RUNTIME: discovery reader + proxies + run() w/ __signature__
    mock_discovery.py      # stand-in for GET /compute/.../tasks?details=true
    __init__.pyi           # STATIC (generated): declares topics
    geostatistics/
      __init__.pyi         # STATIC (generated): re-exports kriging, declustering
      kriging.pyi          # STATIC (generated): typed run(...) -> KrigingResult (+ result classes)
      declustering.pyi     # STATIC (generated)
  generate_stubs.py        # the generator (schemas -> .pyi, inputs AND results)
  demo.py                  # runtime behaviour
  typed_usage_ok.py        # correct usage  -> 0 type errors
  typed_usage_bad.py       # wrong usage    -> 7 type errors
```

The runtime (`__init__.py`) and the static stub (`__init__.pyi`) describe the same
namespace two ways. A type checker reads the `.pyi`; Python runs the `.py`. There is
**no per-task Python class** anywhere — `kriging` is synthesised from the schema,
**inputs and outputs alike**.

## Inputs *and* outputs are schema-driven

The discovery schema describes the **result** as well as the parameters, using the
same semantic vocabulary (`output`, `reference_to`, `supported_schemas`,
`attribute_path`). So the generic engine hydrates the result with **no per-task
output code**:

* `result.target.get_object()` — loads the typed object, dispatched on the runtime
  `schema_id` (mocked here).
* `result.target.to_dataframe()` — generic, polymorphic on the object type.
* `result.target.attribute.reference` — resolved from `attribute_path[schema_id]` in
  the **live** schema, so it **self-heals** if the platform changes that expression.

The generator emits matching typed result classes (`KrigingResult` ->
`KrigingResultTarget` -> `KrigingResultTargetAttribute`, plus `get_object`/
`to_dataframe`), so this output surface is fully typed too.

## Run it

```bash
cd poc-engine

# 1) (Re)generate the stubs from the discovery schemas
python generate_stubs.py

# 2) See the dynamic runtime (no per-task code): listing, signature, execution,
#    schema-driven result hydration, and a task advertised AFTER stub generation
#    that still RUNS live.
python demo.py

# 3) See the static DX the stubs provide (this is what the IDE uses):
pyright typed_usage_ok.py     # -> 0 errors
pyright typed_usage_bad.py    # -> 7 errors, each caught before running
#   (mypy works too: mypy typed_usage_ok.py)
```

## What each part proves

| Claim in Section 6 | Where to see it |
|---|---|
| Namespace `topic.task.run(...)` with **no per-task code** | `demo.py` step 1–3; nothing in `_engine.py` mentions "kriging" |
| Runtime signature / Jupyter `run?` popups work generically | `demo.py` step 2 (`inspect.signature`) |
| **Outputs** hydrate generically from the `results` schema (`get_object`, `to_dataframe`, self-healed `attribute_path`) | `demo.py` step 3; `_engine._ResultNode` is task-agnostic |
| Static **autocomplete + type-checking** for inputs *and* results | `typed_usage_ok.py` / `typed_usage_bad.py` + `pyright` |
| Execution is **live**; hints are **point-in-time** | `demo.py` step 5: `turning_bands` runs live, but pyright flags it (error #5 in the bad sample) until stubs are regenerated |

To see this "in action" open `typed_usage_ok.py` in
VS Code (Pylance) or PyCharm: type `poc_compute_engine.geostatistics.` and you get the task
list; type `kriging.run(` and you get typed, documented parameters; type
`result.target.` and you get the typed result fields + `get_object()`.

## Caveats (it's a POC)

* Reference resolution and object loading are **mocked** (`_engine._mock_resolve`,
  `_engine._load_object`) — out of scope here.
* The server response is **fabricated** from the `results` schema (`_fabricate_output`)
  so the result has something to hydrate; real execution returns it.
* Discovery is a hardcoded dict, not an HTTP client.
* Stubs are regenerated by hand via `generate_stubs.py`; in the real system this
  would run in CI on schema change.
* The one piece that stays hand-authored in a real implementation is the
  `schema_id -> Python loader class` registry — bounded by the object taxonomy and
  **shared across all tasks**, not per-task.
